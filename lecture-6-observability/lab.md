# Лаба 6 — Наблюдаемость, проверенная слепым инцидентом

## Ситуация

Легко построить дашборд, который «всё показывает», когда ты уже знаешь ответ. В этой лабе проверка честная: ты строишь наблюдаемость над `shop`, а потом — **слепой прогон**. Кто-то вносит одну из нескольких неизвестных тебе поломок, и ты, **не зная какую**, должен по алерту заметить проблему и по цепочке метрика → трейс → лог докопаться до причины. Миссия — доказать, что твоя наблюдаемость находит **незнакомое**, а не украшает стену графиками.

Лаба облегчена под скромный ноутбук: одноузловой кластер, `shop` в одну реплику, минимальный стек.

Подопытные сервисы **генерируются AI целиком**. Нужны:

- `api` — HTTP-сервис: `GET /health` → `ok`; `POST /order` → пишет заказ в PostgreSQL; `GET /orders` → читает; `GET /slow` → отвечает с задержкой ~1,5 сек (пригодится для трейсов и графиков задержки);
- `worker` — простой цикл: читает новые заказы из PostgreSQL и помечает обработанными.

PostgreSQL — стандартный образ. Инструментирование трейсами — авто-библиотекой OpenTelemetry, подключается генерацией по описанию (в код лезть почти не нужно). Учебная часть — сама наблюдаемость и расследование.

## Часть 0 — Выбери, как собрать стек

Выбери **один способ** и обоснуй:

- **по кусочкам** — Prometheus + Grafana + Loki (логи) + Jaeger all-in-one (трейсы): больше контроля и понимания, что из чего;
- **готовый комплект** — например, `kube-prometheus-stack` плюс лёгкий сбор логов и трейсов: быстрее поднять.

В README отметь выбор и почему.

## Часть 1 — Разверни shop и стек наблюдаемости

Подними одноузловой кластер (kind/k3d), разверни минимальный `shop` **через конфигурацию** и стек из Части 0. Подключи все три столпа:

- **метрики** — Prometheus скрейпит `/metrics` у `api`;
- **логи** — сервисы пишут в stdout, агент собирает их централизованно (в Loki), так что логи доступны даже после пересоздания пода;
- **трейсы** — `api` и `worker` инструментированы OpenTelemetry, трейсы уходят в Jaeger.

Коротко объясни в README, почему логи пишут в stdout, а не в файлы внутри контейнера (эфемерность из лекции 1).

## Часть 2 — Настрой золотые сигналы

Собери по `api` дашборд с четырьмя **золотыми сигналами**: задержка, нагрузка (запросов в секунду), доля ошибок, насыщение (потребление ресурсов). Прогони немного нагрузки, дёрни `/slow` и убедись, что сигналы на дашборде живые и осмысленные.

## Часть 3 — Найди трейс одного запроса

Прогони один заказ через цепочку `api → worker → postgres` и найди его **трейс** в Jaeger. Покажи дерево span'ов и то, сколько времени ушло на каждом шаге (`/slow` должен наглядно «подсветить» медленный участок). Опиши, как трейс связывается в одно целое (общий идентификатор, проброс по цепочке).

## Часть 4 — Задай SLO и алерт по симптому

Сформулируй **SLO** — цель по надёжности с точки зрения пользователя (например: «99% оформлений заказа быстрее 500 мс»). Настрой алерт, который срабатывает **на риск нарушить SLO** (симптом, который бьёт по пользователю), а не на внутреннюю причину вроде «CPU 90%». В README поясни, почему будить надо по симптомам, а не по каждому спайку.

## Часть 5 — Слепой прогон (кульминация)

Теперь проверка наблюдаемости вслепую. Попроси напарника (или скрипт со случайным выбором) внести **одну из нескольких поломок через конфигурацию**, не говоря тебе какую. Варианты (пусть их будет 3–4):

- занизить лимит памяти PostgreSQL так, чтобы он падал под нагрузкой;
- урезать пул соединений к базе, чтобы `api` начал получать отказы;
- притормозить `worker`, чтобы заказы копились;
- занизить CPU-лимит `api`, чтобы пошёл throttling.

Твоя задача — **не зная, что сломали**:

1. заметить проблему по своему алерту (а не по жалобе пользователя);
2. пройти по цепочке: метрика показала «что» → трейс показал «где» → лог/события показали «почему»;
3. назвать причину и починить.

В README подробно опиши путь расследования — какой сигнал за каким тебя вёл к причине.

## Часть 6 — Убери лишний шум (мониторинг — обязательно)

Наблюдаемость — это не «побольше алертов». Пройди по своим алертам и оставь **ровно 3, которые действительно требуют действия**, обоснуй каждый (что ловит, что делать по нему) и объясни, почему остальное — не повод будить человека (борьба с alert fatigue). Эти 3 алерта и есть обязательная часть мониторинга для этой лабы.

## Что сдать

1. **Код сервисов** `api` и `worker` с Dockerfile (сгенерированные — не оцениваются как программирование).
2. **`README.md`** — выбранный способ сборки стека и почему; как подключены три столпа (Часть 1); дашборд золотых сигналов (Часть 2); разбор трейса (Часть 3); твой SLO и логика алерта (Часть 4); **разбор слепого инцидента** — какую поломку внесли, как ты по трём столпам дошёл до причины (Часть 5); итоговые 3 алерта с обоснованием и рассуждение про alert fatigue (Часть 6).
3. **Твои конфиги** — манифесты/Helm для `shop` и стека, правила алертов.
4. **Скриншоты**: дашборд золотых сигналов; дерево трейса с временами; сработавший алерт; шаги расследования слепого инцидента (метрика → трейс → лог); итоговый набор из 3 алертов.

## Как начать

Открой этот репозиторий со своим AI-ассистентом и попроси помочь с **Лабой 6**. Ассистент настроен вести тебя **по шагам** и проверять понимание — готовое решение он специально не выдаёт. Сгенерируй сервисы `api` и `worker`, а учебную часть веди по шагам с Части 0. Для слепого прогона (Часть 5) удобно работать в паре.

**Если ресурсов мало:** держи `shop` в одну реплику и минимальный стек; при желании — командный режим и несколько ноутбуков.

> **Пользуешься AI?** Убедись, что твой ассистент следует правилам репозитория из файла [`AGENTS.md`](../AGENTS.md). Большинство инструментов подхватывают его автоматически; если твой не подхватил — просто укажи ему на этот файл и попроси действовать по нему.
