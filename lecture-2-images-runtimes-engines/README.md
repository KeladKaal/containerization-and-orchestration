# Лекция 2 — Образы, рантаймы и движки

На первой лекции мы разобрали контейнер как процесс, помещённый в ограничения ядра, и оставили один вопрос открытым: откуда берётся файловая система, которую рантайм подсовывает процессу как корень. Эта лекция отвечает на него и проходит весь стек — от команды `docker run` до работающего процесса.

Три темы: как устроен образ, кто и как превращает образ в запущенный контейнер, и как образ собирается и доставляется между машинами. Сквозной пример — образ сервиса `api` магазина `shop`; для определённости `api` это скомпилированный сервис (например, на Go): по сути один бинарник и немного окружения.

---

## Блок 1. Образ изнутри

### Что такое образ

Образ — это **не** архив и не снимок диска целиком. Это набор **слоёв** плюс метаданные — **манифест** и **конфиг**. Всё описано стандартом **OCI Image Spec** и адресуется по хешам содержимого. Образ **иммутабелен**: собран однажды — не меняется, любое изменение даёт другой образ с другим хешем.

Немного истории. Изначально формат образа был внутренним делом Docker. Когда контейнеры стали индустриальным стандартом, понадобилась вендоронезависимая спецификация — в 2015 году появилась **Open Container Initiative (OCI)** с тремя спецификациями:

- **Image Spec** — как устроен образ (слои, манифест, конфиг);
- **Runtime Spec** — как из распакованного образа запустить контейнер;
- **Distribution Spec** — как образы хранятся и передаются через реестр.

Именно поэтому Docker, containerd, Podman, CRI-O работают с одними и теми же образами.

### Адресация по содержимому

В основе хранения лежит **content-addressable storage**: адрес объекта — это хеш его содержимого (обычно sha256). Такой хеш называют **digest** и пишут как `sha256:3f2a...`. Следствия:

- **дедупликация** — одинаковое содержимое имеет один digest и хранится/качается один раз (общий базовый слой у многих образов — физически один);
- **иммутабельность** — изменил хоть байт → другой digest → это другой объект;
- **проверка целостности** — скачал слой, посчитал sha256, сверил с digest из манифеста.

На этом принципе стоит и хранение, и доставка, и (в конце курса) доверие к образам.

### Слои, манифест, конфиг

**Слой** — это tar-архив изменений файловой системы относительно нижнего слоя: добавленные и изменённые файлы лежат как есть, а удаление кодируется специальным маркером **whiteout** («файл из нижнего слоя считается удалённым»). Слои складываются, а не заменяют друг друга, и порядок важен. Образ `api` снизу вверх: базовое окружение → зависимости → бинарник `api` → метаданные запуска.

**Манифест** — маленький JSON-«оглавление»: ссылка на конфиг по digest, упорядоченный список слоёв по digest, типы содержимого. Сам манифест тоже адресуется по digest — и **digest манифеста и есть настоящий адрес образа**.

**Конфиг** — JSON-«паспорт»: параметры запуска (`ENTRYPOINT`, `CMD`, `ENV`, `WORKDIR`, `USER`, порты), список слоёв в распакованном виде (`rootfs`), история сборки, целевая платформа (архитектура + ОС). Конфиг читает рантайм, когда решает, что и как запускать.

### Как слои становятся файловой системой: overlayfs

Слои — это отдельные наборы файлов, а процессу нужен один корень. Собирает его **overlayfs**, накладывая каталоги друг на друга:

- **lowerdir** — слои образа, только для чтения (их много, стопкой);
- **upperdir** — тонкий записываемый слой самого контейнера;
- **merged** — итоговый вид, который контейнер видит как свой корень.

Это и есть тот корень из лекции 1, на который рантайм делает `pivot_root`. Запись работает по принципу **copy-on-write**: чтение берёт файл из нижнего слоя без копирования; изменение файла из нижнего слоя сначала копирует его в upperdir (**copy-up**), потом правит там; удаление ставит whiteout. Важно: **upperdir эфемерен** — контейнер удалили, записанное исчезло. Поэтому всё, что должно пережить контейнер (данные `postgres`, загруженные файлы), идёт в **тома**, а не в записываемый слой.

### Тег против digest

На образ есть две ссылки. **Тег** (`api:1.4`, `api:latest`) — человекочитаемая метка, которая **может переехать** на другой образ в любой момент. `latest` — не «последняя версия», а просто тег по умолчанию. **Digest** (`api@sha256:...`) — неизменяемый адрес конкретного содержимого. Для воспроизводимости и безопасности (прод, манифесты Kubernetes, цепочка поставки) ссылаются **по digest** (pinning).

Один тег обслуживает разные архитектуры через **image index** (manifest list) — оглавление над манифестами: клиент при загрузке выбирает манифест под свою платформу (`linux/amd64`, `linux/arm64`).

## Блок 2. От движка к процессу

Между командой и процессом — цепочка: `docker` (CLI) → `dockerd` → `containerd` → `containerd-shim` → `runc` → процесс. Это не избыточность, а разделение ответственности. Разберём снизу вверх.

### runc — низкоуровневый рантайм

**runc** — эталонная реализация **OCI Runtime Spec**. На вход получает **bundle**: `rootfs` (распакованный корень образа, обычный каталог) и `config.json` (спецификация: какие namespaces, cgroups, capabilities, seccomp, что запускать). runc делает **ровно то, что мы на лекции 1 собирали руками** через `unshare`/`clone`, только по стандартизированному описанию: создаёт namespaces, вешает cgroups, урезает права, делает `pivot_root`, запускает процесс — и **завершается сам**. За контейнером он не присматривает.

### containerd — менеджер контейнеров и образов

**containerd** — демон, рабочая лошадка ноды. Отвечает за: образы (загрузка, хранение, работа с реестром), **снапшоттер** (готовит `rootfs` через overlayfs из слоёв), жизненный цикл контейнеров (создать/запустить/остановить/удалить). Фактический запуск делегирует вниз, вызывая runc. Самодостаточен: работает и под Docker, и напрямую под Kubernetes. Свои утилиты — `ctr`, `nerdctl`.

### shim — зачем нужен посредник

Если бы containerd был прямым родителем контейнеров, его перезапуск ронял бы все контейнеры (в Linux завершение родителя бьёт по потомкам). Решение — **containerd-shim**, тонкий процесс-посредник на каждый контейнер. runc запускает процесс и уходит, а **родителем остаётся shim**. Он держит потоки ввода-вывода, хранит код возврата и — главное — позволяет перезапустить containerd, не трогая работающие контейнеры (они живут под своими shim, containerd потом переподключается). Когда контейнер завершился, shim сообщает наверх.

### dockerd — обёртка удобства

**dockerd** (Docker Engine) — верхний слой для разработчика: дружелюбный CLI/API (`docker run`, `docker build`, `docker compose`), сети Docker, тома, сборка. Для запуска контейнеров вызывает containerd. Вывод: **Docker — это UX-обёртка над стеком**, а не сам стек; containerd и runc работают без него.

### Полный путь и место Kubernetes (CRI)

`docker run api` → CLI шлёт запрос в `dockerd` → `dockerd` просит `containerd` → `containerd` готовит `rootfs` (overlayfs) и `config.json`, запускает `shim` → `shim` вызывает `runc` → `runc` создаёт namespaces/cgroups/права, делает `pivot_root`, запускает `api` → `runc` уходит, `api` остаётся под `shim`.

Kubernetes не знает про Docker. На ноде работает **kubelet**, он общается с рантаймом по **CRI (Container Runtime Interface)** — стандартному gRPC-контракту: `kubelet → CRI → containerd (плагин CRI) или CRI-O → shim → runc`. Исторически была прослойка **dockershim** к Docker; в Kubernetes 1.24 её удалили — убрали лишний слой, а образы OCI, containerd и runc остались. В современном кластере на ноде обычно containerd или CRI-O, Docker как демон не нужен.

**Суть:** под капотом это тот же стек, что при `docker run`. Разница только в том, кто наверху дёргает за ниточку — человек через `dockerd` или `kubelet` через CRI.

## Блок 3. Сборка и доставка

### Классический сборщик и его ограничения

Старый `docker build` выполнял инструкции Dockerfile строго по очереди, почти каждая — новый слой; кэш линейный (изменилась строка — пересобирается она и весь хвост ниже). Отсюда приём: редко меняющееся (зависимости) — выше, часто меняющееся (код) — ниже. Ограничения: нет параллелизма независимых шагов; грубый кэш; **секреты, попавшие в слой на сборке, остаются в образе навсегда** (удалить следующей инструкцией не поможет — предыдущий слой на месте); сложно кэшировать промежуточное между сборками.

### BuildKit

**BuildKit** — современный движок (в актуальном Docker по умолчанию):

- Dockerfile компилируется в **граф зависимостей** шагов, а не в линейный список;
- независимые ветки графа собираются **параллельно**;
- **точный кэш** по содержимому, с экспортом/импортом (важно для CI на чистой машине);
- **монтируемые кэши** для пакетов и артефактов компиляции — переживают пересборки;
- **секреты и SSH** подключаются как временный mount и в слои **не попадают**.

### Multi-stage и тонкий образ

**Multi-stage build** — несколько стадий в одном Dockerfile. Стадия `builder` содержит полное окружение сборки (компилятор, зависимости) и собирает бинарник `api`; финальная стадия начинается с минимальной базы, куда копируется **только готовый бинарник**. Всё тяжёлое из `builder` в финальный образ не попадает. Результат: вместо сотен МБ с тулчейном — единицы/десятки МБ.

Практики хорошего образа: минимальная база (**distroless** — без пакетного менеджера и оболочки; **scratch** — пустой, для статически слинкованных бинарников); порядок слоёв под кэш; `.dockerignore` (не тащить `.git`, `node_modules`, секреты); фиксировать базовый образ по digest. Общий принцип — не класть в образ ничего «на всякий случай»: меньше поверхность атаки и обновлений.

### Реестр и доставка

**Registry** работает по **OCI Distribution Spec** и по сути состоит из двух хранилищ: **blobs** (слои и конфиги, по digest) и **манифесты** (по digest и по тегу). Реестр отдаёт образ не целиком, а по частям.

`docker pull api:1.4` по шагам:

1. аутентификация — получить токен доступа к репозиторию;
2. запросить манифест по тегу (или индекс → выбрать платформу);
3. прочитать список слоёв и адрес конфига;
4. по каждому слою: если его digest уже есть локально — **пропустить**, иначе скачать blob;
5. проверить sha256 каждого скачанного слоя, собрать образ.

`push` — зеркально: заливаются манифест и недостающие blob-ы; то, что по digest уже есть в реестре, повторно не грузится. Быстрота повторных загрузок — прямое следствие content-addressable-хранения.

### Целостность и доверие

**Digest даёт целостность** (то ли самое содержимое), но **не даёт доверия** (кто это собрал). Поверх образа навешивают: **подпись** (например, `cosign`) — криптографически подтверждает автора/сборку; **provenance** — откуда и как собран (пайплайн, коммит); **SBOM** — список того, что внутри (пакеты и версии), для проверки на уязвимости. Предметно — на лекции 7.

## Итог

- Образ — это слои (изменения ФС) + манифест (оглавление) + конфиг (как запускать); всё по digest; в живую ФС слои собирает overlayfs (lower RO + upper RW, copy-on-write, upper эфемерен).
- Запуск идёт по стеку `dockerd → containerd → shim → runc → процесс`; на дне runc делает работу из лекции 1. Kubernetes использует тот же низ через CRI, без Docker как демона.
- Сборка — BuildKit (граф, параллелизм, точный кэш, секреты вне слоёв) + multi-stage + тонкая база.
- Доставка — реестр по Distribution Spec; pull качает только недостающее по digest; целостность встроена в адресацию, а доверие добавляют подпись и происхождение.
